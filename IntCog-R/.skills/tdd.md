# tdd

> 来源：mattpocock/skills — 红-绿-重构循环
> 适配：Python + pytest，IntCog-R 项目

## 触发条件

用户说"用 TDD 方式"、"先写测试"、"测试驱动"、"红绿重构"。

## 核心原则

**测试验证行为，不验证实现。** 测试通过公共接口描述系统做什么，不关心内部怎么做的。好的测试在重构后仍然通过。

## 反模式：水平切片

```
❌ 错误（水平）：
  RED:   test1, test2, test3, test4, test5  ← 一次性写完所有测试
  GREEN: impl1, impl2, impl3, impl4, impl5  ← 一次性实现所有

✅ 正确（垂直）：
  RED→GREEN: test1 → impl1   ← 写完一个测试，立即实现
  RED→GREEN: test2 → impl2
  RED→GREEN: test3 → impl3
```

水平切片产生垃圾测试：测试想象的行为而非实际行为，对真实变化不敏感。

## 工作流

### 1. 规划

- [ ] 确认接口变更（新增/修改哪些函数、类）
- [ ] 确认要测试的行为（优先级排序）
- [ ] 识别深模块机会（小接口，大实现）
- [ ] 列出行为清单（不是实现步骤）
- [ ] 获得用户确认

### 2. 曳光弹（Tracer Bullet）

写**一个**测试，验证**一件事**：

```python
def test_one_behavior():
    result = module.public_api(input)
    assert result == expected
```

```
RED:   测试失败（预期行为）
GREEN: 写最少代码让测试通过
```

### 3. 增量循环

每个行为重复：

```
RED:   写下一个测试 → 失败
GREEN: 最少代码通过 → 通过
```

规则：
- 一次只写一个测试
- 只写够通过当前测试的代码
- 不要预判未来测试
- 测试聚焦在可观察行为

### 4. 重构

所有测试通过后：
- [ ] 提取重复代码
- [ ] 深化模块（把复杂度藏到简单接口后面）
- [ ] 每次重构后跑测试

**绝对不要在 RED 状态重构。** 先 GREEN，再重构。

## 每轮检查清单

```
[ ] 测试描述行为，不描述实现
[ ] 测试只用公共接口
[ ] 测试在内部重构后仍然通过
[ ] 代码只够通过当前测试
[ ] 没有投机性功能
```
