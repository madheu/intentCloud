# diagnose

> 来源：mattpocock/skills — 六阶段 bug 诊断流程
> 适配：Python 项目 IntCog-R，pytest 测试框架

## 触发条件

用户说"debug"、"排查"、"报错"、"出问题了"、"修一下这个 bug"、"为什么这个测试失败"。

## 核心原则

**先建反馈回路，再读代码。** 没有一个能稳定复现的红色信号，看再多代码也是猜。

---

## Phase 1 — 构建反馈回路

**这是最关键的一步。** 在有一个能抓住 bug 的 pass/fail 信号之前，不要进入 Phase 2。

构建方式（按优先级）：
1. **失败测试**：直接在 bug 所在的 seam 写一个 pytest 测试
2. **CLI 调用**：`python -c "..."` 或 `python script.py`
3. **curl 脚本**：如果涉及 HTTP 接口
4. **最小 harness**：写一个 10 行脚本，只跑 bug 相关的代码路径
5. **二分 harness**：`git bisect run` 自动定位引入 bug 的 commit
6. **差异对比**：新旧版本跑同样输入，diff 输出

**收紧回路**：让回路更快（秒级）、更确定（每次结果一致）、更尖锐（断言精确到具体症状）。

**完成标准**：你能说出一个**命令**，它已经跑过至少一次，能稳定复现这个 bug。

---

## Phase 2 — 复现 + 最小化

- 确认回路产生的失败模式是**用户描述的那个**，不是碰巧的另一个问题
- 将复现场景缩小到**最小**——删掉一切不相关的输入/配置/步骤
- 最小化完成后，**每个残留元素都是必要的**——删掉任何一个 bug 就消失

---

## Phase 3 — 假设

生成 **3-5 个排序假设**，每个必须是**可证伪的**：

> "如果 X 是原因，那么改变 Y 会让 bug 消失 / 改变 Z 会让 bug 更严重。"

**展示排序列表给用户**，等确认后再测试——用户通常有领域知识能瞬间排除某些假设。

---

## Phase 4 — 插桩

- 每次只测一个假设（改一个变量）
- 工具优先级：`pdb` 断点 > 目标日志 > 全量日志
- 所有调试日志用 `[DEBUG-xxxx]` 前缀标记，方便后续 `grep` 清理

---

## Phase 5 — 修复 + 回归测试

- **先写回归测试，再修 bug**
- 把 Phase 2 的最小化复现场景转为测试
- 看它失败 → 修 bug → 看它通过
- 用原始（未最小化）的 Phase 1 回路再跑一次确认

---

## Phase 6 — 清理 + 复盘

- [ ] 原始复现不再出现
- [ ] 回归测试通过
- [ ] 所有 `[DEBUG-xxxx]` 日志已删除
- [ ] 一次性原型已删除
- [ ] 正确的假设写入 commit message

**然后问：什么能防止这个 bug？** 如果涉及架构改进，记入待办。
