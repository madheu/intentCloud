# code-review

> 来源：mattpocock/skills — 双轴审查（标准 + 规格），并行子 agent 执行
> 适配：Python 项目 IntCog-R，使用 pytest

## 触发条件

用户说"review一下"、"审查代码"、"检查一下"、"看看有什么问题"、"代码质量"。

## 执行流程

### 1. 确定基准点

用户指定对比基准（commit SHA、分支名、`HEAD~N`、`main`）。默认 `main`。

```bash
git diff main...HEAD          # 三点的 merge-base 对比
git log main..HEAD --oneline  # 提交列表
```

确认基准点有效且 diff 非空。

### 2. 双轴审查

#### 轴一：标准（Standards）

检查代码是否符合项目规范：

- **项目规范文件**：`DEVELOPMENT_PROGRESS.md`（设计决策）、`config.yaml`（配置规范）
- **通用基线**（Python 项目）：
  - **神秘命名**：函数/变量名不揭示其用途 → 重命名
  - **重复代码**：同一逻辑出现在多处 → 提取共享函数
  - **长函数**：超过 50 行且做多件事 → 拆分
  - **过多参数**：超过 5 个参数 → 考虑 dataclass 封装
  - **原始类型迷恋**：用 str/int 代替领域概念 → 封装为类型
  - **特性依恋**：函数过度访问另一个模块的数据 → 移动到该模块
  - **投机通用性**：为不存在的需求添加抽象 → 删除，内联
  - **消息链**：`a.b().c().d()` 长链调用 → 隐藏在一个方法后
  - **中间人**：类/函数只做委托 → 删除，直接调用

#### 轴二：规格（Spec）

检查代码是否忠实实现了 harness 提示词/issue 的要求：

- 从 harness 提示词中提取要求清单
- 逐项核对：缺失？多余？实现错误？
- 引用原始要求行

### 3. 输出格式

```
## Standards（代码规范）
- [问题] 文件:行号 → 描述 + 违反的规范
- 总结：N 个发现

## Spec（规格符合度）
- [缺失] 要求 → 未实现
- [多余] 实现 → 未要求
- [错误] 要求 → 实现有误
- 总结：N 个发现
```

两轴**分开报告**，不合并排序——一个变更可能标准通过但规格失败，反之亦然。

### 4. 完成后

- 输出两轴各发现数 + 最严重问题
- 不自动修复，等用户确认
