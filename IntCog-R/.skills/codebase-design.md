## 触发条件

设计新模块接口、寻找深化机会、决定 seam 放在哪、让代码更可测试。

## 设计深模块

**深模块 = 小接口 + 大实现**

```
┌─────────────────────┐
│   小接口（少量方法）  │  ← 调用者只需学这一点
├─────────────────────┤
│                     │
│   深实现（复杂逻辑）  │  ← 隐藏在这里
│                     │
└─────────────────────┘
```

反模式 — 浅模块（大量方法 + 薄实现，只是透传）：

```
┌───────────────────────────────┐
│   大接口（很多方法/参数）       │
├───────────────────────────────┤
│   薄实现（只是透传）            │
└───────────────────────────────┘
```

## 设计可测试接口

### 1. 接受依赖，不创建依赖

```python
# ✅ 可测试
def process_order(order, payment_gateway):
    ...

# ❌ 难测试
def process_order(order):
    gateway = StripeGateway()  # 硬编码依赖
```

### 2. 返回结果，不生副作用

```python
# ✅ 可测试
def calculate_discount(cart) -> Discount:
    return Discount(...)

# ❌ 难测试
def apply_discount(cart) -> None:
    cart.total -= discount  # 只在内存中修改
```

### 3. 小接口面积

方法越少 → 测试越少。参数越简单 → 测试 setup 越简单。

## 设计原则

- **删除测试**：想象删除这个模块。如果复杂度消失 → 透传模块。如果复杂度散落到 N 个调用者 → 它在创造价值。
- **接口 = 测试面**：调用者和测试跨同一个 seam。如果需要测试接口之后的东西，模块形状可能不对。
- **一个 adapter 是假设的 seam，两个 adapter 才是真实的 seam**：不要在有东西真正变化之前引入 seam。

## 检查清单

设计新模块时问：
- 能否减少方法数？
- 能否简化参数？（超过 5 个 → dataclass）
- 能否把更多复杂度藏到接口后面？
- 接口和测试面一致吗？
